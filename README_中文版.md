两份 Excel 进去，一份做好的 PPT 出来，一条命令。

```
python monthly.py 2026-04
```

为一家真实的店做的——奥克兰一家健康产品零售店，卖保健品、奶粉和蜂蜜，客户既有到店的，也有海外代购转寄的。以前出一次月报要在 Excel 里耗掉大半天，现在大约四分钟，而且跑它的人是店长，不是开发。

这里的代码跑的是**合成数据**。真实的单品销售额和供应商名单属于这家店，所以 `tools/make_synthetic_data.py` 生成了一份替身数据集，品牌全是编的，但保留了真实四个月的形态，包括二月出口量的塌陷——那正是报告必须解释的东西。

## 产出什么

*（这里有一张四页拼图）*

一份十二页的 PPT：核心数字、四个月的金额与件数趋势、品类构成、畅销品、品牌排行、自提结构、保健品功能分类的月度变化、本地与出口渠道走势、销售额集中度，以及当月的运营情况。

`output/2026-04/` 里有一份完整样例——PPT，以及生成它用的 `report_data.json` 和图片。它是用 `--no-llm` 生成的，所以你看到的每一句都是规则拼出来的兜底文案；没有 API key 的人 clone 下来看到的就是这个。

图表是 matplotlib 画的 PNG；文案是 PPT 里真正的文本框，不是烤进图片里的。每个标题和备注要么是语言模型写的、并已对照源数据校验，要么——在没有 API key 时——用同一批数字按规则拼出来。

## 问题是什么

这家店有自己的销售数据，但看不见它。

收银系统导出一张很宽的表：一行一个 SKU，每个月三列（`jan_order`、`jan_qty`、`jan_amt`）。另一张表按渠道拆分销量。一个店长想知道的所有事——主推的精品动没动、哪些品牌在涨、二月为什么断崖——全在里面，而把它们捞出来意味着一下午的数据透视表。

有三件事让它不只是个画图练习：

**品类不在数据里。** 导出的表里没有任何字段说明某个 SKU 是保健品还是奶粉，也没说它是不是门店主推的那一批。这些知识长在店长脑子里。它必须被采集一次然后记住，否则每个月的工作量都一样。

**有意思的波动需要数据之外的背景。** 二月出口量跌了 40%。数据库不可能知道春节是 2 月 15 到 23 号，以及跨境货运在前后各停摆约两周。

**跑它的人不是技术人员。** 一条每月都要有人去改 SQL 文件的流水线，第三个月就会被弃用。

## 最想聊的部分：校验模型写的数字

语言模型描述一张表时，偶尔会产生一个看着对、其实不存在的数字。

这事真的发生了。当月销售额是 **78,427.85**，生成的标题写着 **84,427.85**。没有崩溃，没有违反任何规则，这个数字就上了一份送到店主手里的 PPT 的封面。

prompt 里**已经**写了"只使用数据里的数字"，写得很清楚。模型还是漏了一位。这才是值得提炼的教训：**对于数值输出，prompt 不是控制手段，是请求。** 所以改成机械校验，而不是信任。

`pipeline/grounding.py` 把生成文本里所有像数字的片段抠出来，逐个确认它出现在 `report_data.json` 或节假日表里（允许四舍五入的误差）。发现分成两类：

| | 含义 | 怎么办 |
|---|---|---|
| `missing` | 源数据里根本没有——很可能是编的 | 发出去之前必须核 |
| `sign_only` | 量级对得上，符号相反 | 扫一眼方向词对不对 |

这个拆分比听上去重要。`sign_only` 一直在响，而且几乎总是无害的——模型把存的 `-42.35` 写成 "fell 42.35%"，比带个减号读着顺。**不拆开的话，常见的无害情况会淹掉罕见的严重情况，整个校验一个月内就没人看了。**

分词器里有两个特例，都来自真实的误报：

```python
if token.startswith("-"):
    following = text[match.end():]
    if DATE_WORDS.match(following):
        token = token[1:]          # "15-23 Feb" —— 这是区间，不是负号
```

早期版本把 `15-23 Feb` 读成了 15 和 −23，然后把一个完全正确的节日日期报成"查无出处"。而最直觉的修法——把数字之间的连字符一律当区间——更糟：它会把真正的 `-42.35%` 变成正数，而那恰恰是伪造可以藏身的地方。同时满足两者的规则很窄：**只有当连字符后面的数字紧跟着一个日期词时，它才是区间分隔符。**

校验发现问题时，step 13 返回退出码 3，`run_report.py` 会在整轮结束、打印完文件名之后**把警告再说一遍**。打在中间的警告会在画图时滚走；等有人注意到，错的数字已经在 PPT 上了。

`tests/test_grounding.py` 的第一条测试就是复现那次伪造。

## 语言模型被允许做什么

```
算术  ->  Python（step 12，在 `computed` 里）
措辞  ->  模型
```

报告引用的每个百分比都在 SQL 和 Python 里算好、取整，然后作为一个**成品数字**交给模型。prompt 禁止它推导任何新的，"再简单也不行"。早期版本让模型自己从原始月度合计算环比，它产生了数据里任何版本都不存在的数字。

模型真正的活儿很窄：**读一个已经正确的数字，说出它意味着什么。**

二月渠道那页，两条路径分别给出：

**规则拼的**——committed 的样例 PPT 里就是这个，也是没有 API key 时你会得到的：

> Export fell 40.0%, local fell 9.1%
> （出口跌 40.0%，本地跌 9.1%）

**模型写的**，且已通过 grounding 校验：

> Export volume fell 40.0% while local fell only 9.1% — a gap consistent with the Chinese New Year freight pause (15–23 Feb) rather than a change in local demand
> （出口量跌 40.0%，本地只跌 9.1%——这个差距与春节货运停摆（2月15–23日）相符，而非本地需求发生了变化）

两句都准确，引用的是同样两个预先算好的数字。第二句是店长能据以行动的那句。归因来自作为上下文加载的节假日表，而且做了对冲措辞，因为数据支持的是相关性，不是因果。

要在自己的数据上看到这个效果：带 key 跑一次 step 13，把生成的 `narrative.json` commit 进去——它只是一个字符串组成的 JSON 文件，之后每次构建 PPT 都会直接用它，不再调 API。

### prompt 是一份过往错误清单

`step13_generate_narrative.py` 带着十五条编号规则。每一条的存在都是因为模型真的干过它禁止的事，而且**规则和起因一起保存**——一条不写原因的规则，会被下一个觉得它啰嗦的人删掉。

| 规则 | 起因 |
|---|---|
| 不许算任何新百分比 | 从原始合计推环比，造出了不存在的数字 |
| tier 不是价格档 | 把 premium 说成"高价值"、regular 说成"低价走量款" |
| 不许跨品类比品牌 | 拿奶粉品牌和保健品品牌比销售额——单价差十倍，这么比毫无意义 |
| 每个字段只用自己那页的数据 | 在"占全店"那页引用了"占品类"的比例——图看起来像错的 |
| 不许下判断，好坏都不行 | 开头写"证明了我们策略的有效性" |
| 只给门店层面的动作 | 建议重新谈供应商条款，那不是读者能定的 |
| 方向词必须匹配符号 | 把下跌说成增长 |

第四条是最微妙的。两个数字都是真的，都在源数据里，grounding 校验也通过了——那个数字只是**在回答一个和旁边那张图不同的问题**。机械校验能抓住编造，抓不住放错位置的真数字。那仍然需要一条 prompt 规则和一个读者。

`tier` 也值得一说。它标记的是门店希望店员推荐的那批货。它**不是**价格档——便宜的纪念品可以是 premium，贵的奶粉可以是 regular。我给过这份 prompt 的每个模型都默认它是价格档，然后开始写顾客消费能力，所以这条纠正现在放在 system prompt 的最前面。

## 设计决策

### 数据库就是记忆

`dim_product` 存着每个 SKU 的品类、精品档和发货方式。一个商品分过一次类，就再也不会被问第二次。

这是让整件事可持续的原因。第一个月问了 60 个品牌，第四个月只问了 4 个——只有真正的新品。**人工量自己往零收敛，不需要谁去维护一份映射表。**

### 两个机器不该替人回答的问题

`run_import.py` 只为两件事停下来，退出码 `2`——意思是"需要人"，和表示失败的 `1` 区分开：

1. **一个没有品类的品牌。** 新供应商，还没人说过他们卖什么。
2. **一个和自己品牌不一致的商品。** 归在奶粉品牌下的"绵羊胎盘素 60 粒"——通常品牌是对的，是这个商品例外。

这两件事一旦猜错，就会污染此后每一份报告，而且结果看不出任何异常。所以它们变成一份带空格的 CSV，填好之后接着跑。答案落进 `dim_product`，再也不问。

### 精品判定用规则，不用 SKU 清单

```python
PREMIUM_BRANDS = ["orama", "nonie", ...]        # 整个品牌
SKU_RULES = [
    {"brand": "clearfield", "keywords": ["immune", "digestion"],
     "local_pickup_only": True},                 # 品牌的一部分
]
```

第一版是一串 SKU 编码。供应商换版时编码会变，精品属性不会。`tier_rules.py` 在**导入时**就会报错，如果一个品牌同时出现在两个清单里——那种组合会让收窄规则永远走不到，成为一段看起来能用的死代码。（我在这个仓库里就写出过这个 bug，被这道守卫抓住了。）

### 模糊匹配阈值是量出来的，不是拍的

品牌名进来时拼写不一致——大小写、少个空格、偶尔的错字。`difflib` 配 0.85 能处理。

阈值定低了会**悄悄合并两个真实品牌**：一个品牌的销售额消失进另一个的柱子里，而图看起来完全合理。所以这个常数由测量支撑，还有一条测试盯着它——遍历所有确实不同的品牌两两算相似度，断言最接近的一对仍在阈值以下。真实清单上最差的一对是 0.706。

### 报告月份只有一个开关

`report_config.rpt_period`——一行，一个值，所有查询都读它。

它是一张表而不是会话变量，因为每个脚本各自开连接，在一个脚本里 set 的 `@变量` 到下一个就没了；那会产生看起来像"缺数据"而不像报错的 NULL。`config_id` 主键让"改月份"成为真正的 upsert——没有它，改月份可能插进第二行，而每个查询都是 `LIMIT 1`。

### 降级，而不是失败

没有 API key，或者调用失败？PPT 照样出。每个标题回退成用同一批数字拼的句子——准确，只是平淡些。在 PPT 代码里这就是一个函数：

```js
function text(field, fallback) {
  const value = N[field];
  return (typeof value === "string" && value.trim()) ? value.trim() : fallback;
}
```

**某个晚上做不出来的报告，比一份平淡的报告更糟。** 这也意味着你可以 clone 这个仓库、不用 API key 就得到一份完整的 PPT——`python monthly.py 2026-04 --no-llm`。

### 稀疏事实表

`fact_sales` 里没有行，意思是"没卖"，不是"卖了0"。给每个 SKU 在每个没卖的月份都写一行零，会让表大约膨胀二十倍而不增加任何信息，而 `SUM` 跳过缺失行本来就返回你要的结果。

### 重跑永远安全

所有入库都是 `INSERT ... ON DUPLICATE KEY UPDATE`，键是 `(period, store, sku)`。同一个月导两次是覆盖，不是翻倍。这件事比听上去重要——**人对"刚才成功了吗"的自然反应就是再跑一遍。**

## 改变了设计的那些 bug

只挑教会我东西的，不是完整清单。

**一个没有上界的趋势查询。** 出三月报告时，趋势图里出现了四月的数据。所有查询都过滤了 `period >= start`，没有一个过滤 `period <= rpt_period`，因为写代码的时候**还没有**更晚的月份。没有任何报错；图只是安静地在描述一个和标题不同的月份。现在每个趋势查询都带 `period <= rpt_period`，还有一条边界测试。

**归档的通配符。** `output/2026-02/` 里总是多出三月的 PPT。归档那步用 `*.pptx` 从工作目录里捞，捞到什么算什么。唯一的症状是一个本该有一个文件的文件夹里有两个——而如果你打开了错的那份，会看到一份关于错误月份的、看起来完全合理的报告。现在文件名带月份，多余的会被清掉。

**环比卡片显示了错的月份。** 渠道那页取的是**跌得最狠**的月份，而不是**最近**的——我是对着二月写的，那时两者恰好相同。三月的 PPT 印出了二月的 −40%。**只覆盖你当时在想的那种情况的测试数据，只会确认你已经相信的东西。**

**月份名写死在四个地方。** 加四月要改四个脚本，漏掉一个就会在跑到一半时 `KeyError`——一次只暴露一个，来回好几轮才修完。逐个修错误出现的地方是错误的本能；把它们全部从 `months_for()` 派生出来才是修法。

**step 2 抹掉了手填的品类。** 它每个月从头重建品牌-品类 CSV，把店长手工分好的 25 个品牌清空了。下一轮又把它们全问一遍。现在有三级优先：上一次的 CSV 优先，然后是已知默认值，最后才是空白。

**非交互终端上的 `getpass()`。** 永远挂着、没有任何输出，这是最糟的失败方式——它看起来像"在慢慢跑"。现在会直接抛错，并说出该设哪个环境变量。

**硬编码在五个文件里的密码。** 我干的，第一版。改成了环境变量且没有默认值，还有一条测试断言那个默认值没长回来。

## 怎么跑

### 依赖

MySQL 8、Python 3.10+、Node 18+（只有出 PPT 那步用）。

```bash
git clone <这个仓库> && cd retail-report-pipeline

python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
npm install

cp .env.example .env        # 填 MYSQL_PASSWORD
set -a && source .env && set +a

mysql -u root -p < sql/schema.sql
```

### 合成数据集

`data/raw/` 里已经有四个月。要重新生成：

```bash
python tools/make_synthetic_data.py
```

### 跑一个月

```bash
python monthly.py 2026-01     # 第一个月：会停下来让你分类
# 填好它指名的那个 CSV
python monthly.py 2026-01 --resume

python monthly.py 2026-02     # 问得少了
python monthly.py 2026-03     # 更少
python monthly.py 2026-04
```

没有 `ANTHROPIC_API_KEY` 就加 `--no-llm`，PPT 会用规则拼的文案构建。

### 店长每个月的操作

1. 把两份 Excel 放进 `data/raw/`
2. 往 `data/reference/monthly_context.csv` 加一行——进店人次、活动说明（这些不在收银系统里，要人手填）
3. `python monthly.py 2026-05`
4. 回答它停下来问的问题，然后 `--resume`

## 仓库结构

```
monthly.py                 每月一条命令
run_import.py              Excel → 数据库，遇到需要判断的地方停下
run_report.py              数据库 → PPT，结束时重复警告

pipeline/
  config.py                月份配置、路径、从环境变量取凭据
  db.py                    连接、报告月份开关、读 dim_product
  tier_rules.py            精品/普通规则，品牌模糊匹配
  grounding.py             数值校验器
  step01..step07           解析与分类（人工检查点在这里）
  step08..step11           入库 MySQL
  step12_fetch_report_data.py    所有查询 → JSON；所有算术
  step13_generate_narrative.py   模型、prompt 规则、校验
  step14_render_charts.py        matplotlib
  step15_build_deck.js           pptxgenjs

sql/schema.sql             星型模型，注释里写了理由
tools/make_synthetic_data.py   生成 data/raw/
tests/                     pytest
data/reference/            人工维护：品类、例外、节假日、月度背景
output/<月份>/              成品 PPT，以及生成它的 JSON 和图片
```

为什么一个 Python 项目里有一个 JS 文件：`pptxgenjs` 表达这套版式所需的代码量大约是 `python-pptx` 的三分之一，而两者的边界是一个 JSON 文件，所以两边用什么语言不必一致。

## 关于数据

`data/` 里的一切都是合成的。品牌、商品名和门店都是编的；数字是按真实数据集的形态生成的——四个月、二月的低谷、一条独立于本地的出口渠道——但不复现任何真实的商业数字。

二月那次变动是**设计出来的**，不是随机的：出口量跌 40%，本地跌 9%，三月双双回升。这个不对称正是报告必须解释的东西，也正是节假日归因逻辑值得存在的原因。
